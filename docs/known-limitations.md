# Known limitations

The converters favour a faithful, explicit result over a clever guess. Where something cannot be translated it is dropped and recorded in `state.dropped`, rejected with an error, or replaced by a text note. The list below is what a user is most likely to run into. Feature identifiers refer to [feature-inventory.md](feature-inventory.md).

## Reasoning

- Only a leading `<think>...</think>` block in content is parsed as reasoning. A model whose chat template opens the think block in the prompt, so the reply contains only a closing `</think>`, needs `thinkOpen: true`; the stream then emits nothing until the `</think>` arrives or the stream ends (FI-081, [#23](https://github.com/CLDMV/llm-translator/issues/23)).
- Reasoning blocks produced by the translator carry a marked signature (`llmt:...`). They are not Anthropic signatures and are not accepted by real Anthropic endpoints. When an OpenAI client talks to an Anthropic upstream, assistant reasoning in history is dropped unless `reasoningRoundTrip` is on and the client replays the `reasoning_details` items it was given (D-46).
- `redacted_thinking` blocks are dropped. Thinking `display` modes and `between_tools` thinking have no effect.
- Servers that require reasoning to be sent back on every turn (DeepSeek with tools, OpenRouter's structured `reasoning_details`) are supported through `reasoningRoundTrip` (on for the DeepSeek driver). It depends on the client keeping the signature of each thinking block; a client that drops thinking blocks, or `clear_thinking` removing old turns, leaves nothing to restore. Such a turn is sent without reasoning, one warning is printed per upstream, and the server may refuse it (DeepSeek's refusal is explained in the error). OpenRouter and its `reasoning_details` shapes have not been verified against the real service (no driver yet, [#41](https://github.com/CLDMV/llm-translator/issues/41)).

## Tools

- Anthropic server tools (`web_search_*`, `web_fetch_*`, `code_execution_*`, `tool_search_*`) are dropped. A request that only carries such tools reaches the model with no tools. Server tools: [#5](https://github.com/CLDMV/llm-translator/issues/5).
- Anthropic's client tools (`bash_*`, `text_editor_*`, `computer_*`, `memory_*`) are sent to other upstreams as ordinary function tools with the input fields Anthropic documents (see [protocol-support.md](protocol-support.md)). Anthropic's own model has the schema and the usage instructions built in; another model only sees the description the translator wrote, so it may call these tools less reliably than Claude does. Anthropic also adds text to the system prompt for these tools. The translator adds the memory tool's protocol and the opening of the computer use prompt, the only parts Anthropic publishes; nothing is added for bash and the text editor, and the rest of the computer use prompt is not published. A version released after the table was written is dropped like a server tool until a schema for it is added.
- `server_tool_use` and server tool result blocks in history are dropped; `pause_turn` is never produced.
- Only one content block streams at a time. With the default `toolStreaming: "buffer"`, every tool call is held until the stream finishes and then delivered as one complete block in index order, so tool arguments are not displayed incrementally (total completion time is unchanged, and pings cover the silence). Text and thinking still stream and always appear before the tool blocks. With `toolStreaming: "stream"`, arguments stream incrementally for the first call, later parallel calls arrive as whole blocks, and text that arrives while a tool block is open is held until the tool blocks are done, so it appears after them.
- Streamed tool-call arguments are forwarded as received. Truncated JSON (for example after a `length` stop) reaches the client as is, but the stop reason is then `max_tokens` instead of `tool_use`; non-streaming replies wrap invalid arguments as `{ "_raw_arguments": "..." }`.
- Claude Code's tool search works through the translator (`toolSearch`: `expand` by default), but it costs the model an extra `ToolSearch` call before it can use a deferred tool, and it has not been run against a real backend yet ([#65](https://github.com/CLDMV/llm-translator/issues/65)). Small models that do not call tools reliably should use `ENABLE_TOOL_SEARCH=false` in Claude Code. See [claude-code.md](claude-code.md#tool-search).
- Chat Completions has no error flag on tool messages, so `is_error` on a tool result becomes a text prefix (`toolErrorMarker`, `"[error] "` by default) on every Chat Completions upstream. Set `toolErrors: false` to send the text unchanged. In the other direction the marker is read back as `is_error` only with `toolErrorInference` on (off by default, because a tool that prints the marker would be taken for a failure).
- When an Anthropic client's request goes to vLLM's own `/v1/messages` (the default with vLLM 0.11.1 and later, or `api: "messages"`), which has no assistant prefill, `document` block or `metadata.sampling` support; the first two are converted instead and the last is dropped. Thinking signatures from that endpoint are not Anthropic's (vLLM makes up an id, and the translator marks blocks that have none). Prompt caching markers are ignored there too. See [drivers](drivers.md#native-v1messages-for-vllm) (FI-137).
- Readiness probing (`GET /health`) is wired for vLLM only, and only on the request path of a model that has more than one endpoint; a lone endpoint is not probed until `health.check()` is called. A probe is a verdict for `healthInterval` (10 s by default), so an endpoint can be tried up to that long after it died, and the request then fails over as before (FI-139).
- An adapter that vLLM loads at runtime is routable only after the model list was fetched again (a client calling `/v1/models`, `model.list()`) or `detect()` ran; the translator does not poll for it.
- Tool-call ids are reformatted only for an upstream whose driver declares `toolCallIds` (FI-067, [#20](https://github.com/CLDMV/llm-translator/issues/20)). Only the `mistral` driver declares it, so any other server with a strict id format still sees the client's ids. An id the upstream makes itself passes to the client as it is (sanitized to the Anthropic pattern on the Anthropic front).
- `strict` tools are carried to the upstream and their schemas are checked against the strict subset, but the translator cannot tell whether a server really enforces them: the `vllm` driver reports that it can, and enforcement there depends on its `--tool-strict-level` setting. Schemas outside the subset are reported and sent without `strict`, so that tool is not enforced. Tracked in [#120](https://github.com/CLDMV/llm-translator/issues/120).
- LocalAI decides parallel tool calls per model (`function.parallel_calls` in its YAML) and returns tool calls as plain text when its parser does not match the model's format; the translator cannot enable parallel calls or parse text calls, see [LocalAI](drivers.md#localai).

## Content

- `document` blocks with a `url` source are a text note unless the `documentUrls` setting is on (FI-046, [#18](https://github.com/CLDMV/llm-translator/issues/18)). With it on, only `application/pdf` and `text/plain` are fetched, only from hosts on its allow-list, and a document that cannot be fetched is a note rather than an error. Nothing is cached, so a retried request downloads the document again. `image` blocks with a `url` source are forwarded to the upstream as URLs and are not fetched.
- The file store behind `/v1/files` is small and local to the translator: files are not shared between translator instances (unless they share a `files.dir` directory store), uploaded files cannot be downloaded through the Anthropic front (Anthropic refuses that too; the OpenAI front serves them), and only PDF and plain text files can be referenced as documents and images as images. Responses API `input_file` and `input_image` with a `file_id` are still refused. Anthropic's `container_upload` blocks and files created by Anthropic's own tools are not supported. Ids the store does not hold are forwarded on a native route (they may be the upstream's own files) and refused on a converting one; see [protocol-support.md](protocol-support.md#24-files-a-to-o-and-o-to-a).
- PDF page images are only produced when the model accepts images, `@napi-rs/canvas` loaded, and the page budget (`pdf.maxImages`) allows. Scanned PDFs without a text layer yield empty page text; there is no OCR.
- Encrypted or corrupt PDFs fall back to a text note. PDFs over 100 pages or 32 MB are rejected with an Anthropic-shaped error.
- A text-only model behind a non-vLLM upstream is only discovered on the first request that carries an image: that request is sent twice (the second time without images) and the model is remembered as text-only for the rest of the process. The wording match is deliberately conservative, so a server that refuses images with an unusual message still returns its 400; set `images: false` for it. See `imageFallback` in [settings](settings.md).
- Audio, video and file-by-id inputs on the OpenAI side are dropped when converting to Anthropic. File references: [#17](https://github.com/CLDMV/llm-translator/issues/17).
- Assistant prefill depends on the chat template; templates that inject thinking into the generation prompt may behave unpredictably.

## Requests and responses

- `n` greater than 1 is answered by fan-out only for an OpenAI client talking to an Anthropic-protocol upstream (FI-097): `n` requests are sent, so the upstream bills and rate-limits `n` calls, the branches do not share a seed (Anthropic has none), and a pool whose first endpoint speaks the OpenAI protocol is sent `n` as is, so a failover to an Anthropic endpoint then fails with `unsupported_field`. An `n` above 128 is rejected. On the Anthropic front `n` does not exist.
- Sampling and penalty fields without an Anthropic equivalent (`seed`, `logprobs`, `logit_bias`, `frequency_penalty`, `presence_penalty`, and so on) are dropped when converting to Anthropic. Newer Anthropic API versions also reject `temperature`, `top_p` and `top_k` themselves.
- Constrained decoding (`constraint`) covers what each backend documents: llama.cpp has no regex constraint, TGI no grammar, and other OpenAI-protocol upstreams only a JSON Schema. On vLLM a constraint is dropped when the request offers tools, because vLLM applies it to the whole generation (FI-031, FI-138, [#14](https://github.com/CLDMV/llm-translator/issues/14)). The field names come from each backend's documentation and have not been run against a real server. A request sent to vLLM's own `/v1/messages` (`nativeMessages`) does not get the constraint: the extension is removed from `metadata` and nothing is mapped.
- Prompt caching hints (`cache_control`) are dropped. `cache_creation_input_tokens` is always 0; cache reads are reported only when the server exposes `cached_tokens`. `cache_salt` (vLLM) and `prompt_cache_key` (OpenAI) are the only hints that are mapped, and no per-API-key setting exists beyond the `authorize` hook's `cacheSalt`; see [Prompt caching](server.md#prompt-caching) (FI-040, FI-100, FI-136, [#15](https://github.com/CLDMV/llm-translator/issues/15)).
- When a server returns no usage (or only one side of it), a converted reply carries estimates for the missing side (the server tokenizer's count or one token per four characters) instead of zeros, and a usage report keeps them apart in `estimated`. Replies passed through without conversion are not altered, and on the Anthropic front `message_start` still reports 0 input tokens because the estimate is only known at the end of the stream (FI-074, [#22](https://github.com/CLDMV/llm-translator/issues/22)).
- `context_management` is emulated for `clear_thinking` and `clear_tool_uses_20250919`. Other edit types (compaction, anything unknown) are dropped and recorded in `state.dropped`. `clear_thinking` is not listed in `applied_edits`. Tracked in [#13](https://github.com/CLDMV/llm-translator/issues/13).
- `clear_tool_uses_20250919` runs in the translator, on the converted OpenAI messages, so it differs from Anthropic's in these ways (Anthropic counts exactly, on its own tokenizer):
  - Input tokens, for `trigger` of type `input_tokens` and for `clear_at_least`, are estimated at one token per four characters of the messages and tools (the estimate `token.count` falls back to). The server's tokenizer is not asked, so a trigger fires somewhat earlier or later than it would on Anthropic, and `cleared_input_tokens` is an estimate of the characters removed.
  - `trigger` applies when its value is exceeded: more than `value` estimated input tokens, or more than `value` tool uses in the history. The default is 100000 input tokens.
  - `keep` (`{ type: "tool_uses", value }`, default 3) protects the most recent tool uses of the conversation, whatever tool they are, so a tool listed in `exclude_tools` still occupies a place in that window.
  - `exclude_tools` is compared with the tool names the client sent. A tool use named there is never cleared.
  - Clearing goes from the oldest tool use forward. A cleared result becomes `[Tool result cleared to save context]`; the call itself stays, and with `clear_tool_inputs: true` its arguments become `{}`. A tool use that has no result yet and an already cleared result are left alone.
  - `clear_at_least` (`{ type: "input_tokens", value }`): when clearing would free fewer estimated tokens, nothing is cleared and the edit is not reported.
  - Images a tool returned are sent by the converter as a separate user message after the result; those are not cleared.
  - An edit whose parameters are not of the documented shape (an unknown threshold `type`, a value that is not a non-negative integer, `exclude_tools` that is not a list of strings, `clear_tool_inputs` that is not a boolean) is dropped as a whole.
- Non-standard finish reasons (`abort`, `eos`, `error`, and similar) are treated as `end_turn`. Tracked in [#27](https://github.com/CLDMV/llm-translator/issues/27).
- `stop_details.category` is set only from Azure OpenAI style `content_filter_results` (a filtered `hate`, `sexual`, `violence` or `self_harm` gives `general_harms`); every other upstream gets null, because none of them reports which policy fired (D-50, [#123](https://github.com/CLDMV/llm-translator/issues/123)). Anthropic's `cyber`, `bio`, `frontier_llm` and `reasoning_extraction` are never produced. `model_context_window_exceeded` is never produced.
- Structured output is limited to `response_format` JSON Schema. Native grammar, regex and choice constraints of individual servers are not exposed. Tracked in [#14](https://github.com/CLDMV/llm-translator/issues/14).
- The response `model` echoes the model the client asked for, not the one the upstream reports.
- `anthropic-version` and `anthropic-beta` are ignored.
- Ollama's native `/api/chat` mode (`api: "ollama.chat"`) cannot force a tool call (`tool_choice` other than `auto` is dropped), has no `n` above 1, `logit_bias` or `logprobs`, and takes images as base64 only. The `efforts` levels, the image and tool retries and `passthroughFilter` do not apply to it, and streamed thinking and tool calls follow Ollama's documented line shape without having been run against a real server ([#70](https://github.com/CLDMV/llm-translator/issues/70)).
- Requests that go over the Responses protocol (`api: "responses"`, or a Responses client under `api: "auto"` while the upstream has it) are stateless: `store` is `false`, the whole conversation is sent on every call, and `previous_response_id`, `conversation`, background mode and the server-side tools (web search, file search, code interpreter, MCP) are not used. `stop`, `seed`, the penalties, `logit_bias`, `logprobs` and `top_k` have no Responses field and are dropped. The driver's request, response and chunk leaves, the image and tool retries, `passthroughFilter`, the sampling and constraint extensions, the `efforts` level lists and the server tokenizer do not apply to them. Reasoning only round trips when the server returns `encrypted_content` (it is asked for, and a server that leaves it out gives thinking text without a way to send the reasoning back). Nothing has been run against a real Responses server yet: the field and event names come from OpenAI's API reference. Only `api: "auto"` falls back from `/v1/responses` to Chat Completions (on a 404, 405 or 501); an explicit `api` never does (see [drivers.md](drivers.md#responses-api-v1responses)).

## Google Gemini native API

- Nothing has been run against real Google services (the Gemini API or Vertex AI); the shapes follow Google's API reference and the tests use a local stand-in ([#70](https://github.com/CLDMV/llm-translator/issues/70)).
- Embeddings and the Live API are not served.
- `urlContextMetadata` (which URLs the URL context tool fetched, with a status) is not carried: it says what was retrieved, not which part of the answer it supports, so it has no citation to give.

## Amazon Bedrock

- Nothing has been run against real AWS; the SigV4 signer matches AWS's published test vectors and the rest follows the documentation ([#70](https://github.com/CLDMV/llm-translator/issues/70)).
- Only Claude (InvokeModel, Anthropic body) and Converse are served. The provider-specific InvokeModel bodies of other model families (Titan, Llama, Mistral, Cohere) are not. Embeddings and image models are not served. `CountTokens` serves only the models Bedrock lets it count, and the estimate is used for the rest.
- Credentials come from the upstream's settings, the `AWS_*` variables, the shared config files (a profile with keys, a `credential_process`, an SSO login, a role to assume or a web identity), the web identity of the environment, the ECS task role and the EC2 instance role. A profile with `mfa_serial` is refused, because nothing here can ask for the one-time code. An SSO login is renewed only when it is an `sso_session` one that cached its refresh token and client registration; otherwise (and when the registration has expired) `aws sso login` is the fix. A machine with no credential waits for the metadata service for a second before the error unless `AWS_EC2_METADATA_DISABLED=true` is set.
- Over Converse, reasoning is sent back only when its signature came from the same upstream through this translator (a thinking block from anywhere else is sent as nothing), cache points follow the Anthropic `cache_control` markers block by block, at most four are kept, and a model that rejects `cachePoint` needs `settings.bedrock.cache: false`. `response_format` is a forced tool, so the model cannot be forced while thinking is on and then only follows the instruction to answer through the tool. Guardrails and citations are not read.
- Converse needs a `toolConfig` whenever the history has tool calls or results, and has no `tool_choice: "none"`. A request without tools therefore has its past tool calls and results written as text (`[Called tool Read with input {...}]`, `[Result of tool Read: ...]`, `[Tool Read failed: ...]`), and `tool_choice: "none"` with tools sends the tools and adds a system instruction not to call any, so it is a request to the model and not a guarantee.
- Over InvokeModel, Anthropic API features Bedrock lacks (`mcp_servers`, `container`, Files) are removed or refused by Bedrock, and a beta that Bedrock does not know is refused by it.

## Cohere

- Nothing has been run against the real Cohere API; the shapes follow the documentation ([#70](https://github.com/CLDMV/llm-translator/issues/70)).
- Cohere's documentation does not say whether a model needs its past `thinking` blocks sent back; they are sent, as the request schema allows. Checking that against the real API is part of [#70](https://github.com/CLDMV/llm-translator/issues/70).
- `logit_bias` and `top_logprobs` are dropped and named in `state.dropped`. Cohere has no field for either (its `logprobs` gives the log probability of each generated token and no alternatives), so this is a limit of the protocol and not open work.
- Structured output (`response_format`, `output_config.format`) next to tools or documents is a system instruction to reply in that JSON, because Cohere does not take the format together with them. The model follows the instruction; the format is not enforced, and a reply can still be something else.
- Token counts use Cohere's tokenizer on the text the model reads, and the chat template's few tokens per message are not counted, so a count runs slightly below what Cohere bills.

## Streaming

- A stream that ends without `finish_reason` and without `[DONE]`, or with no data, becomes an `error` event rather than a completed message.
- Pings are not produced by the pure stream converters; the SSE writer adds them while the upstream is silent.
- Stream converters accept SSE text or bytes, iterables and parsed chunks, but a single malformed SSE data line ends the stream with an error event.

## Responses front

- The Responses API is served statelessly, on the OpenAI front only. `previous_response_id`, `conversation`, `store: true`, `background: true`, stored prompts and `item_reference` input items are refused ([#8](https://github.com/CLDMV/llm-translator/issues/8)); hosted tools and their `*_call` items are refused ([#9](https://github.com/CLDMV/llm-translator/issues/9)). There are no `GET`, `DELETE` or cancel routes for responses.
- Only function tools, text and image (`image_url`) input are mapped. `input_file`, `input_audio`, file ids and custom tools are refused.
- Reasoning is returned as a summary part, never as raw `reasoning_text`. A reasoning item is replayed to the upstream only with `reasoningRoundTrip`; otherwise it is dropped.
- A `<think>` block in the content of an OpenAI-protocol upstream is not split into a reasoning item (the Anthropic-front conversions do that, a pass-through chat reply does not).
- `top_logprobs`, `max_tool_calls`, `truncation: "auto"` and `context_management` are dropped; `logprobs` on output text is always empty.
- Upstream-protocol use of the Responses API (calling `/v1/responses` on a backend) is separate work ([#7](https://github.com/CLDMV/llm-translator/issues/7)).

## Out of scope

- Message Batches, Files, Skills, Conversations, Realtime, audio, image and moderation endpoints are not provided. Embeddings are forwarded to OpenAI-protocol upstreams only. Batches: [#25](https://github.com/CLDMV/llm-translator/issues/25), [#29](https://github.com/CLDMV/llm-translator/issues/29); Responses: [#4](https://github.com/CLDMV/llm-translator/issues/4).
- Server-side features of the Anthropic platform (MCP connector, container, fast mode, service tiers, task budgets, server-side fallback) have no equivalent on local servers.
- Google Vertex AI (driver `vertex`) is Claude over `rawPredict` only. Workload identity federation and impersonated credentials are not read (pass `getToken`), the model list is the configured `models` because Vertex AI has no Models API, and the features Vertex AI does not offer (Files API, URL sources, MCP connector, Message Batches and others) are forwarded and refused by Google rather than removed or emulated. Not run against the real service yet: [#70](https://github.com/CLDMV/llm-translator/issues/70).
- Backend-specific behaviour beyond what the vLLM, llama.cpp, SGLang, Ollama, LM Studio, TGI, LocalAI, OpenAI, Azure OpenAI, Vertex AI, DeepSeek, Mistral, OpenRouter, Groq, Together, Fireworks, xAI, Gemini's OpenAI-compatible endpoint, Anthropic and generic OpenAI-compatible drivers implement (other hosted providers) is not special-cased yet. Driver issues start at [#33](https://github.com/CLDMV/llm-translator/issues/33).
