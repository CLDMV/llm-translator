# Settings

Settings tune how the converters map one protocol onto the other. They are resolved in layers with later layers winning: library defaults, then detected or probed values, then driver defaults, then global `settings`, then per-endpoint `settings`. Undefined values never override an earlier layer. The `pdf` object merges key by key; every other key is replaced whole. Enumerated keys are validated and an invalid value throws a `TranslatorError` with the code `invalid_setting`.

Every converter accepts an optional `settings` argument (partial objects are fine) and resolves it with `resolve()` from `src/lib/settings.mjs`, so direct callers get the same defaults as the server.

## Reference

| -------------------- | -------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `inlineSystem`       | `"auto"`                   | `"auto"`, `"keep"`, `"hoist"`, `"user"`, `"drop"`        | How `role: "system"` messages found inside `messages` (Claude Code sends them on every turn) are handled. `user` folds the text into the adjacent user turn wrapped in `<system-reminder>` tags, which keeps order and the prompt prefix stable between turns. `keep` forwards a system message in place (only safe when the chat template accepts one). `hoist` appends the text to the leading system message. `drop` discards it. `auto` behaves like `user` in the converters; the vLLM driver can resolve it to `keep` after probing the chat template. |
| `stripBillingHeader` | `true`                     | boolean                                                  | Remove the `x-anthropic-billing-header: ...` system block. | `reasoningField`     | `"reasoning"`              | `"reasoning"`, `"reasoning_content"`                     | Field used when sending reasoning to an OpenAI-style server (assistant history, and streamed or returned reasoning when the OpenAI front is used). ## Where settings come from

The vLLM driver derives some values from the detected server version (for example `reasoningField` and `thinkingBudget`), the `compatible` driver uses conservative defaults, and each upstream in the configuration can pin its own `settings`. The server layer documents the configuration file; this page covers the converter keys only.

## Examples

A text-only model behind vLLM 0.15, with Claude Code's deferred tools turned off at the client:

```json
{
	"settings": {
		"images": false,
		"reasoningField": "reasoning_content",
		"inlineSystem": "user",
		"toolSchema": "sanitize"
	}
}
```

Rejecting anything the translator cannot map instead of dropping it:

```json
{ "settings": { "unknownFields": "error", "documents": "error" } }
```
